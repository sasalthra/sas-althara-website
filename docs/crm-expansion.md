# توسعة CRM — حالة التنفيذ والتشغيل الآمن

هذه نسخة محلية غير منشورة. لم تُشغَّل أي migration على قاعدة حقيقية، ولم يُختبر مزود AI مدفوع أو مصدر Sheets فعلي. كانت معظم ملفات التوسعة موجودة كتعديلات غير ملتزم بها عند بدء هذه الجولة؛ تمت مراجعتها واختبارها، واستكمال الوصول من الواجهة وإعدادات Sheets والتقويم والإجازات المؤرخة واختبارات التخزين. لا تعني نتيجة build أن إعداد الإنتاج مكتمل.

## الوظائف المتاحة

- جدول مشترك RTL بمحاذاة بداية النص للرؤوس والخلايا، مستخدم للعملاء والمتابعات والعقارات والمعاملات والحضور والاستيراد. يحتفظ عمود الهاتف باتجاه LTR ومحاذاة يمين صريحة.
- اختيار «أخرى» مع وصف إلزامي للعقار؛ يتحقق الخادم منه ويحفظ `property_other` ويعرضه في قائمة العميل وملفه.
- استيراد `.xlsx` من المتصفح: اختيار الورقة وصف العناوين، ربط الأعمدة، معاينة، تطبيع أرقام الجوال العربية والسعودية، تمييز التكرار والأخطاء، تأكيد قبل الإدخال. يحفظ الصف الأصلي للمستورد في `crm_import_rows`. الملف الأصلي لا يتغير. لا تُحسَب صيغ Excel ولا تُنفَّذ خلاياه كأوامر. التقرير JSON يتضمن الصفوف غير المستوردة. حد 2MB/1000 صف/100 عمود.
- المعاملات مرتبطة بالعميل؛ العقار ومصدر العميل والمبيعات والميدان مستمدة من رابط العميل، وموظف التمويل مربوط بمعرف مستخدم فعال. حقول الورقة الإضافية للوسيط والمصروفات الخارجية وعربون المشتري وصافي العمولة موجودة. `د=` مرفوض ولا يُنشأ له حقل.
- القاعدة المالية الوحيدة المحسوبة: **سداد الشركة + السعي** عند سداد الشركة، و**السعي فقط** عند سداد العميل بنفسه. الأرقام سلاسل عشرية ويحسب الجزء المؤكد بدقة السنتات عبر BigInt. لا يدخل سداد العميل المباشر تلقائياً في تحصيل الشركة. الضريبة والإجماليات والرصيد وصافي العمولة يدوية؛ ليست معادلات معتمدة. حفظ المعاملة يتطلب تأكيداً وصلاحية admin ورقم إصدار يمنع استبدال تعديل أحدث.
- HR: ملف وظيفي، جدول وأيام عمل وموقع ودقة وسماح يضبطها admin فقط، تسجيل حضور/انصراف بوقت الخادم، قفل صف الموظف ومنع التكرار، سجل تدقيق، تقويم شهري مع التأخير والإجازة المعتمدة، طلبات الخدمات التسع وقرار إداري مع ملاحظة دون اعتماد المستخدم لطلبه. طلب الإجازة له تاريخ بداية ونهاية متحقق منهما. الموظف يرى بياناته فقط؛ admin يستطيع مراجعة الجميع.
- إعدادات Sheets من تبويب للإدارة فقط؛ مفاتيح الوصول لا تظهر في الواجهة. تبويب الاستيراد للإدارة والمشرف. تبويب AI لجميع مستخدمي CRM، لكن إعدادات المزود للإدارة فقط.
- AI: مفتاح المزود يُدخل في المنتج ويحفظ مشفراً AES-256-GCM على الخادم مع ربط التشفير بالمزود. OpenAI أو Anthropic وطراز يدخله admin. أداتان فقط للقراءة: ملخص مراحل العملاء المصرح بهم، وحضور المستخدم نفسه. موافقة إرسال البيانات إلى المزود، حد 20 طلباً/ساعة، تدقيق، لا SQL أو تنفيذ كود أو أدوات كتابة.

## قاعدة البيانات — شرط قبل الاستخدام

لا تستخدم قاعدة WordPress أو قاعدة الإنتاج للتجارب. `node scripts/migrate-local.mjs` يعرض خطة فقط ولا يفتح اتصالاً ولا يقرأ `.env`.

لبيئة اختبار جديدة ومعزولة فقط، بعد مراجعة SQL:

1. أنشئ قاعدة اختبار محلية فارغة باسم يطابق `sas_*_test` ومستخدماً مقيداً بها.
2. اضبط `MIGRATION_HOST` على loopback و`MIGRATION_DATABASE`, `MIGRATION_USER`, `MIGRATION_PASSWORD` و`MIGRATION_PORT` عند الحاجة، عبر مدير أسرار؛ لا تضع القيم في Git أو المحادثة.
3. شغل `node scripts/migrate-local.mjs --apply-local` فقط في تلك البيئة. لم ينفذ هذا الأمر أثناء العمل الحالي.
4. يقرأ السكربت `db/mysql/001_leads.sql` و`002_expansion.sql` ثم يضيف أعمدة العملاء المفقودة ويوسع `stage` إلى `VARCHAR(40)` لحفظ المراحل القديمة والجديدة.
5. **الترقية لقاعدة قائمة ليست مجرد إعادة CREATE IF NOT EXISTS**: طابق مخططها أولاً. إذا طبقت نسخة أقدم من توسعة HR، يلزم إضافة `hr_requests.start_date CHAR(10) NULL` و`end_date CHAR(10) NULL` بعد فحص وجودهما. لا تخمن تواريخ الطلبات القديمة؛ تبقى NULL حتى مراجعتها. راجع collation والمفاتيح الخارجية وجداول المستخدمين والنشاط قبل اعتماد ترقية staging. سكربت local لا يعالج جميع فروق مخططات منشآت سابقة.
6. استخدم DB_* لبيئة التطبيق الاختبارية فقط، وراجع `NEXTAUTH_URL`؛ بوابة origin ترفض الكتابة عندما لا يطابق أصل الطلب أصل هذا المتغير.

## إعداد Google Sheets والجدولة

1. يعتمد admin **مصدر العملاء الفعلي**؛ نموذج معاملات المستخدم ليس تلقائياً مصدر الاستيراد. مزامنة المعاملات من workbook ليست منفذة.
2. أنشئ حساب خدمة Google بصلاحية `spreadsheets.readonly` وشارك الجدول معه كقارئ فقط. اضبط على الخادم `GOOGLE_SHEETS_CLIENT_EMAIL` و`GOOGLE_SHEETS_PRIVATE_KEY` عبر إدارة الأسرار. لا تحفظهما في المتصفح.
3. من «إعدادات Google Sheets» أدخل معرف المستند فقط، نطاقاً مثل `Leads!A1:D1001`، العناوين الأصلية بترتيبها، وربط الأعمدة. يجب أن يكون صف العناوين الأول. الاسم والجوال مطلوبان، وعمود وصف العقار الآخر مطلوب إن لم يوجد معرف عقار صالح. تغيير العناوين يوقف القراءة بدلاً من تفسير أعمدة مختلفة بصمت.
4. فعّل المصدر وأكد اعتماده؛ احفظ ثم راجع الحالة المقروءة من الخادم. «مضبوط» تعني وجود الإعداد وليس نجاح اتصال Google.
5. أنشئ `CRON_SECRET` عشوائياً بطول لا يقل عن 32 حرفاً على الخادم. اضبط مجدول الاستضافة لاستدعاء `GET /api/integrations/sheets/sync` عبر HTTPS مع `Authorization: Bearer <secret>` بالتواتر الذي يعتمده المسؤول. احفظ السر في إعداد protected header لا في عنوان URL أو سجل أمر. الجدولة ليست داخل عملية Next.js ولا تعمل لمجرد فتح التبويب.
6. تشغيل يدوي من التبويب يستخدم جلسة admin وطلب POST وتأكيداً صريحاً. راجع `last_run` و`last_result`؛ يسجل أرقام الصفوف غير الصالحة دون أسماء. اختبر تكرار التشغيل في staging.
7. المزامنة **إضافة فقط**: لا تحدث ولا تحذف عملاء موجودين. التكرار بحسب الجوال، وليس معرف مصدر خارجي؛ لا يوجد استيراد تفاضلي/ثنائي الاتجاه. حد المصدر 1000 صف؛ يجب تقسيم الأكبر بإجراء معتمد، ولا يُستنتج أن كل المصدر استورد عند زيادة حجمه.

## إعداد HR

- أنشئ مستخدمي CRM المحليين أولاً؛ الملفات الوظيفية تستخدم UUID للمستخدم، وليس هوية Google الإدارية النصية.
- من تبويب الموظفين كـ admin اضبط القيم الحقيقية: الإحداثيات، نصف القطر، أقصى دقة، الأيام، البداية والنهاية، المنطقة الزمنية IANA، والسماح. لا توجد إحداثيات أو دوام افتراضيان للشركة.
- الحضور يحتاج HTTPS وإذن الموقع. يرفض التسجيل إذا كانت المسافة **مع هامش الدقة** خارج النطاق. GPS بالمتصفح ليس وسيلة مضمونة ضد الانتحال.
- اختيار الشهر ثم «عرض الشهر» يقرأ السجلات من الخادم؛ التقويم للإدارة يسمح اختيار الموظف. الأيام المجدولة تعتمد الإعداد الحالي وليس أرشيف تغيرات الدوام. عدم التسجيل ليس غياباً محسوماً أو خصماً.
- رصيد الإجازة يدوي؛ اعتماد الطلب لا ينفذ خصم رصيد أو دفعة مالية أو تغيير سجل حضور. الطلبات الأخرى تجمع التفاصيل ويُسجل القرار فقط. يلزم تصميم واعتماد قواعد الرصيد/العطلات والتداخل والورديات الليلية والتصحيح والمطالبات والأرصدة قبل ترحيلها آلياً.

## إعداد AI وحدوده

- اضبط `APP_ENCRYPTION_KEY` كـ 32 بايت عشوائية بترميز Base64 على الخادم عبر مدير أسرار. ليس مفتاح المزود. غيابه يمنع الحفظ؛ تغييره دون ترحيل التشفير يمنع فك المفاتيح المحفوظة. احفظ نسخة محمية وسياسة تدوير.
- يحفظ admin مفتاح المزود من المنتج. GET لا يعيد المفتاح ولا ciphertext. لا تجعل أي متغير `NEXT_PUBLIC_*` يحمل أسراراً.
- يرسل السؤال ونتيجة الأداة إلى المزود فقط بعد الموافقة؛ راجع سياسة خصوصية الشركة. لا يُرسل اسم/جوال العميل في ملخص المراحل.
- **غير منفذ:** أدوات AI للحذف/المالية/التعديلات الجماعية وموافقاتها المتعددة. هي ممنوعة بالكامل حالياً، وليست أزراراً تدعي التنفيذ. يلزم تصميم خطة عمل محددة وصلاحيات لكل كيان وتوقيع موافقة وربطها بالقيم والإصدارات قبل فتح أي أدوات كتابة.

## التحقق المنفذ

- `npm test`: ناجح؛ يتضمن اختبارات auth والعملاء، المخطط المالي وOther والتكرار والتشفير وSheets والسياسة الجغرافية وواجهات API والتقويم وSSR لمساحة العمل.
- `scripts/check-storage-expansion.mjs`: SQL حقيقي في SQLite بذاكرة معزولة، مع استبدال driver MySQL والجلسة فقط. تحققت إعادة الاستيراد دون تكرار، حفظ الوصف والصف الأصلي، rollback عند فشل التدقيق، حفظ/تحديث المعاملة ورقم الإصدار، الحضور والانصراف ومنع التكرار وخروج الموقع، الإجازة واعتمادها وعزل قراءة موظف آخر. ترجمة upsert وحذف FOR UPDATE في الاختبار لا تثبت سلوك أقفال MySQL الفعلي.
- `npx tsc --noEmit`: ناجح، وأعيد بعد اكتمال البناء. `npm run build`: ناجح على Next 16.3.5 مع webpack؛ جميع المسارات الجديدة مضمنة. لم يلزم تعديل كود التطبيق بعد تحديث الاعتماديات.
- lint المستهدف لملفات التوسعة وAPI والسياسات والاختبارات: أعيد ونجح دون أخطاء. lint كامل المشروع بعد تحديث eslint-config-next: **13 خطأ و8 تحذيرات**؛ التحذير الإضافي من قاعدة `@next/next/no-location-assign-relative-destination` في `app/crm/auth-buttons.tsx` الذي لم يتغير. فُحصت نسخ HEAD من الملفات الخمسة ذات الأخطاء عبر ESLint stdin بالإعداد الجديد وثبت نفس مجموع 13 خطأ؛ أخطاء سابقة في effects وروابط الصفحة الرئيسية داخل workspace وusers-panel وlead detail وsite-header وصفحة العقار. تم استبعاد test-output المولد فقط، لا إخفاء قواعد التطبيق. انتهت المحاولة الأولى بمهلة 180 ثانية؛ أعيد الفحص بمهلة 600 ثانية واكتمل.
- تحذير Node SQLite التجريبي متوقع؛ رسائل database unavailable في اختبار العملاء فشل مصطنع لا اتصال فعلي.
- `git diff --check`: ناجح. لم يحدث commit أو push أو deploy أو تعديل ملفات البيئة أو اتصال ببيانات العملاء.

## تحديث اعتماديات الأمان المحلي

- تحقق سجل npm و`npm audit` فعلياً: قبل التحديث 5 ثغرات إنتاجية (1 حرجة، 3 عالية، 1 متوسطة) و9 لجميع الاعتماديات. بعد التحديث: `npm audit --omit=dev` و`npm audit` كلاهما **found 0 vulnerabilities**. هذه نتيجة قاعدة advisories وقت الفحص وليست تدقيقاً أمنياً شاملاً للتطبيق.
- رُفع `next` و`eslint-config-next` من `16.2.6` إلى `16.3.5` بتثبيت إصدار صريح. إصدار Next المنشور يعتمد `postcss 8.5.23` و`sharp ^0.35.4`، ويتوافق مع React `19.2.6` والإعداد الحالي. لا overrides ولا `audit fix --force`.
- تحديثات lock المتوافقة مع نطاقات الحزم: `sharp 0.34.5 → 0.35.4`، `postcss 8.4.31` المتداخل و`8.5.14` الجذري إلى `8.5.23` موحد، `nanoid 3.3.12 → 3.3.19`، `baseline-browser-mapping 2.10.30 → 2.11.23`. أُصلحت أيضاً اعتماديات التطوير: `@babel/core 7.29.0 → 7.29.7`، `brace-expansion 1.1.14 → 1.1.18` و`5.0.6 → 5.0.9`، `browserslist 4.28.2 → 4.28.9`، `js-yaml 4.1.1 → 4.3.2` مع اعتمادياتها المطلوبة.
- بيئة التحقق: Windows، Node `24.13.0` وnpm `11.6.2`. يجب أن تستخدم الاستضافة إصدار Node مدعوماً ضمن `>=22.13.0 <25` بحسب package.json، وتنفذ تثبيتاً من lock وبناءً جديداً على نظامها؛ لا تنقل node_modules الخاص بـ Windows إلى Linux.
- ملفات هذه الجولة فقط: `package.json` و`package-lock.json` وهذه الوثيقة. حُفظت تغييرات التوسعة السابقة؛ لم يعدل كود التطبيق أو SQL أو ملفات الأسرار، ولم تتم مزامنة مجلد website.
- **شرط SQL للنشر لا يزال مفتوحاً:** خذ backup واختبر استعادته، افحص مخطط staging الفعلي، راجع `001_leads.sql` ثم `002_expansion.sql` والأعمدة الإضافية المبينة أعلاه. طابق أنواع/collations معرفات العملاء والمفاتيح الخارجية، وأضف تواريخ HR المفقودة فقط بعد الفحص؛ `CREATE TABLE IF NOT EXISTS` لا يرقّي الجداول القائمة. يلزم اختبار rollback وأقفال InnoDB والتزامن وصلاحيات مستخدم التطبيق قبل اعتماد خطة إنتاج. شُغّل سكربت migration في وضع PLAN فقط؛ لا اتصال بقاعدة حقيقية ولا تطبيق SQL.
- **بوابات الأمان غير المحسومة:** مراجعة سحب صلاحية الجلسة فور تعطيل المستخدم، تغطية rate limits لجميع endpoints، حدود فك ضغط xlsx، صلاحيات الأدوار والاحتفاظ ببيانات العملاء. لا تعتبر صفر advisories أو نجاح build إغلاقاً لهذه البنود أو تصريحاً بالنشر.

## بوابات ما قبل الإنتاج — غير مكتملة

1. migration/rollback على MySQL staging حقيقي، واختبارات تزامن الأقفال وتعارض التعديل ونسخة احتياطية.
2. رحلة واجهة كاملة بحسابات اختبار ومراجعة المحاذاة البصرية على الهاتف/سطح المكتب؛ SSR اختبر RTL والمحاذاة المنطقية وليس قياسات البكسل في المتصفح.
3. اختبار workbook اصطناعي من ملف فعلي عبر المتصفح، ومصدر Sheets staging والجدولة والتوقف عند انجراف العناوين. لا تستخدم workbook العملاء كبيانات اختبار تلقائية.
4. اختبار خدمة المزود الفعلية بإذن مالي منفصل؛ لم يجر أي اتصال مدفوع.
5. اعتماد صيغ الضريبة وصافي العمولة والإجماليات والرصيد وسياسات HR ومسارات الاعتماد، وتوسيع الحقول المنظمة للطلبات غير الإجازة عند اعتمادها.
6. نظام إشعارات مستقل/دفع وبريد غير منفذ؛ الحالة وملاحظة القرار والإعلانات تظهر داخل HR عند التحديث.
7. مراجعة أمن وصلاحيات الجلسات وتعطيل الحسابات، rate limits لجميع endpoints، ضغط ملفات xlsx والمصادر الكبيرة، واحتفاظ البيانات قبل نشرها العام.

النسخ إلى مجلد website يقتصر على قائمة ملفات مع hashes قبل/بعد وتحقق عدم تغير الهدف. لا يُستبدل المجلد كاملاً ولا `.git` أو `.env` أو بيانات العقارات أو node_modules. ملف activity الموجود في GitHub وغير الموجود بالنسخة الثانية ليس ضمن التغييرات الجديدة؛ على المسؤول مراجعته مستقلاً إن كانت صفحة تفاصيل العميل في النسخة الثانية تحتاجه.
